### Résolu ce run → **BT1 + BT2**

Thème : **single-home resilient batch loop**.

- Nouveau helper `runResilientBatch<T>(items, handler, onItemError): { successCount, errorCount }` dans `src/infra/pg-boss/queue-worker.helper.ts` (à côté de `registerScheduledQueueWorker`/`registerJobQueueWorker`).
- Isole les échecs par item (log via callback + `continue`), renvoie les compteurs pour le summary log de l'appelant.
- 3 workers migrés : `production.worker`, `crown-production.worker`, `barbarian-seeding-catchup.worker`.
- Wording des logs d'erreur + summary logs **inchangés** (passés en callback / gardés côté appelant) → comportement byte-for-byte préservé.
- Handler typé `Promise<unknown>` (les services renvoient une valeur ignorée — ex `updateProduction`).
- 3 tests unitaires ajoutés (`queue-worker.helper.spec.ts`) : all-success, isolation d'un item en échec + continuation, liste vide.

### Looks bad but fine

- `registerScheduledQueueWorker` / `registerJobQueueWorker` : déjà consolidés (run précédents), boilerplate `onModuleInit` minimal. RAS.
- `world-lifecycle.worker.ts` : 5 boucles `for world` **différentes** (comptage via `updateMany` en tx, guards `continue`, pas de try/catch per-item). Fusionner avec le batch resilient forcerait une abstraction fourre-tout. Laisser.
- 64 `NotFoundException` : messages/shapes divergents, pas un dédoublonnage propre. Laisser.
- `combat.worker.ts` (2044L) / `combat.service.ts` (1602L) : gros mais couverts par smokes ; split = L effort risqué (W1/B1 backlog).
