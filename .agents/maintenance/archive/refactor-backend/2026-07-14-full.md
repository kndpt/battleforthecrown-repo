# refactor-backend — 2026-07-14 — DUP-PLANNER

## Thème

Consolidation des deux planners de notification capture-window byte-identiques
(`event-outbox-notification-planner.ts`).

## Contexte / finding

`DUP-PLANNER` (Med, candidat #1 du run précédent).

- `planCaptureWindowOpened` (`event-outbox-notification-planner.ts:166-185`) et
  `planCaptureWindowInterrupted` (`:187-206`) avaient des corps **strictement
  identiques** — seule différait la string du `payload as <Type>`.
- Routing identique : résout l'attaquant (`payload.attackerUserId ??
  getAttackerUserIdByConquest(pendingConquestId)`), pousse la copie complète à
  l'attaquant, puis résout le défenseur live via `getUserIdByVillage(
  targetVillageId)` et pousse une copie scrubbée (attacker fields retirés) si
  distinct.
- Les deux payloads partagent structurellement `{ pendingConquestId: string;
  targetVillageId: string; attackerUserId?: string }` (cf.
  `packages/shared/src/events/types.ts:156` et `:180`).

## Changement

- Ajout d'une interface locale `AttackerRoutedCaptureWindowPayload` (le sous-set
  structurel commun).
- Fusion des deux consts en un seul `planCaptureWindowAttackerRouted:
  AnyPlanner`, câblé sur les deux kinds dans `PLANNERS`.
- Imports `VillageCaptureWindowOpenedPayload` /
  `VillageCaptureWindowInterruptedPayload` supprimés (devenus inutilisés) ;
  `VillageCaptureWindowCompletedPayload` conservé (planner distinct, ne fusionne
  pas — routing par snapshot, pas de résolution live).
- Net : -1 planner (~24 lignes de duplication en moins), zéro changement de
  comportement.

## Sécurité type

Move pur. `scrubAttackerFields` retire `attackerUserId` + `attackerVillageId` ;
`attackerVillageId` absent du payload Interrupted → `delete` no-op inoffensif,
comportement préservé. Le cast `payload as AttackerRoutedCaptureWindowPayload`
est aussi sûr que les deux casts d'origine (même provenance, payload validé Zod
en amont via `PayloadForKind`).
